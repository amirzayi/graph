# Task Service

## Test

### End to End

در سناریوی تست End to End، به‌صورت BlackBox و بدون استفاده از کد پروژه، به لبه‌ی سرور درخواست فرستاده و APIها را با همه وابستگی‌ها (مثل rate limit، authentication token) تست می‌کنیم. به این شکل، در صورت از کار افتادن هر یک از api‌ها، middleware یا router تست fail شده و متوجه خواهیم شد.

### Mock

کاربرد mocking برای زمانی است که بخواهیم رفتار یک چیز را تقلید و پیاده‌سازی کنیم؛ مانند یک سرویس خارجی، و عملکرد سرویس خودمان را در تعامل با آن تست کنیم. برای مثال این کار روی task service انجام شده است.

مثل دنیای واقعی: درگاه پرداخت — تقلید رفتار درگاه پرداخت و تست عملکرد کد در حالت‌های:

- پرداخت موفق
- پرداخت رهاشده
- پرداخت ناموفق (کنسل‌شده)

## Tradeoff

### Microservice vs Monolithic

انتخاب بین میکروسرویس و مونولیت، موضوع مهمی در طراحی معماری سیستم‌های نرم‌افزاری است که هرکدام مزایا و معایب خاص خود را دارند.

با انتخاب میکروسرویس، تفکیک سرویس‌ها از یکدیگر باعث می‌شود سرویس‌ها مستقل از هم اجرا شوند؛ به‌طوری‌که از کار افتادن هرکدام تأثیر مستقیمی روی بقیه ندارد (fault tolerance). همچنین مقیاس‌پذیری آن با افزایش تعداد پروسس‌ها قابل انجام است.

از معایب این معماری این است که در صورت وجود وابستگی بین سرویس‌ها، عملاً قابلیت fault tolerance از دست می‌رود و طراحی درست boundary context نقش بسیار مهمی در این معماری دارد. در مقابل، در معماری مونولیت، بروز مشکل در یک بخش می‌تواند باعث از کار افتادن کل برنامه شود و مقیاس‌پذیری آن کمی پیچیده‌تر است.

همچنین مدیریت تراکنش‌های دیتابیس، به‌دلیل استقرار جداگانه‌ی سرویس‌ها، با چالش‌هایی روبه‌رو است که راه‌حل‌های متنوعی برای آن وجود دارد؛ در حالی‌که در معماری مونولیت این موضوع به‌سادگی قابل پیاده‌سازی است.

در صورت نیاز به ارتباط بین سرویس‌ها، برخلاف مونولیت که از IPC استفاده می‌کند، نیاز به ارتباط sync یا async وجود دارد که این موضوع باعث ایجاد مقداری تأخیر شبکه می‌شود.

### Clean vs Tightly Coupled Architecture

در معماری وابسته (tightly coupled)، توسعه‌ی کد بسیار ساده است، چون با دنبال کردن توابع فراخوانی‌شده، روند برنامه مشخص است. اما در معماری تمیز (clean)، این وابستگی وجود ندارد و اجزای مختلف برنامه صرفاً از طریق قرارداد (contract) با هم تعامل دارند و نسبت به یکدیگر اطلاعی ندارند.

مزیت استفاده از معماری تمیز این است که امکان پیاده‌سازی الگوی adapter/port یا ساختار modular را فراهم می‌کند؛ به این صورت که تنها با تغییر handler می‌توان مشخص کرد که مثلاً داده در دیتابیس ذخیره شود یا از طریق REST/gRPC به یک سرویس دیگر ارسال شود. اما برتری tightly coupled این است که کد برنامه زمان کامپایل به بایت کد تبدیل شده و به‌دلیل عدم استفاده از حافظه جهت ذخیره‌ی وابستگی‌ها مانند دیتابیس یا سایر سرویس‌های موردنیاز، Garbage Collector نیازی به اسکن حافظه‌ی Heap ندارد و باعث بهینه شدن مصرف حافظه توسط برنامه خواهد شد.

در این نمونه‌کد از معماری کد تمیز استفاده شده تا امکان mocking توسط لایه‌ی بالایی و جایگزینی با استفاده از Dependency Inversion فراهم شود؛ برای مثال برای audit log امکان نوشتن روی کنسول، فایل، لاگ یا دیتابیس و... وجود دارد، بدون اینکه کد task manager تغییری کند.

همچنین در این نمونه‌کد از ساختار modular استفاده شده تا سرویس task به‌صورت یک ماژول مستقل و بدون اطلاع از بقیه‌ی سرویس‌ها فعالیت کند. با استفاده از این طراحی در معماری مونولیت، یک ماژول به سادگی قابل جداسازی به میکروسرویس خواهد بود.

### Anemic Model vs Rich Model

گاهی اوقات ساختار کد کسب‌وکار با مدل (دیتابیس) همخوانی ندارد و با یکسان‌سازی، آنومالی دیتابیس رخ می‌دهد، یا با اعمال منطق کسب‌وکار روی کد مدل باعث ایجاد fat model خواهد شد که با هر تغییری، نتیجه‌ی خروجی api و کدهای وابسته تغییر می‌کند. با پیروی از Anemic Model، مدل کسب‌وکار از دیتابیس تفکیک شده و با استفاده از تبدیل ساختار مدل با anti corruption layer فقط ساختار مورد نیاز کسب‌وکار در سرویس استفاده شده و به‌سادگی مدل دیتابیس از رابطه‌ای به nosql قابل جایگزینی است.
